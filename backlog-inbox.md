  <researcher_notes>Owner decision (2026-07-10): explicitly chose to keep LazyOffice's own chat/plan/approve window rather than let Claude Desktop's UI become the front end (that alternative — Claude Desktop as the chat UI, LazyOffice exposed as an MCP tool it calls — was researched and offered first; Owner picked the CDP-automation path instead, after being shown the risk tradeoff). Researched before building: there is no supported way to send Claude Desktop a prompt programmatically. The only known technique (a third-party PoC, github.com/epiccoleman/claude-automator, explicitly labeled "no credit or responsibility taken") launches Claude Desktop with --remote-debugging-port and scrapes its DOM via Playwright/CDP through undocumented, unstable CSS selectors. Built engine.callLLM on that technique: attach over CDP, start a new conversation per call (keeps requests from bleeding into each other, at the cost of zero shared context between calls), type systemPrompt+userPrompt as one combined message (Claude Desktop's chat box has no separate system-prompt field), click Send, poll div.font-claude-message every second and treat two consecutive unchanged reads as "done" (no completion event exists). Verified against a stand-in only: a real Chromium window launched with --remote-debugging-port showing a fake page with the same DOM shape, revealing canned responses gradually (~2-3s) to exercise the stability-polling logic for real — confirmed checkStatus/getPlan's clarification loop/classifyAttachments/buildContent+createOutput all work end-to-end and that streamed text is never read early. Never run against a real Claude Desktop app — every selector is unverified and may already not match the current UI. Flagged explicitly (in mac-claude-desktop/README.md and in conversation) as scraping a consumer product's UI through an undocumented mechanism, gray-area against the product's intended use, and fragile by construction — Owner made this choice with that risk stated plainly, twice.</researcher_notes>
